# Laires Story Change Loop — Implementation Plan

## Context

Laires already behaves like a narrative analysis workbench:

- it holds a structured narrative graph
- it can analyze scenes into graph state
- it supports read-only critique in Consultant mode
- it supports direct manuscript edits in Workshop mode

What it does not yet fully do is close the loop after story changes.

For a coding harness, the loop is usually:

1. Change code
2. Re-run targeted analysis/tests
3. Compare before vs after
4. Tell the user whether the change improved or regressed the system

For Laires, the equivalent loop should be:

1. Change story text
2. Detect which story regions are now stale
3. Re-analyze only the affected regions
4. Recompute narrative evaluators on affected scopes
5. Compare before vs after
6. Tell the writer what improved, what regressed, and what remains uncertain

This plan adds that loop without turning every edit into a full-book LLM rerun.

## Product Goal

Make Laires feel like a true fiction harness by giving it an automatic, incremental post-edit review loop.

The loop should:

- trigger from normal writing activity
- stay cheap for small edits
- expand scope only when needed
- surface clear before/after feedback
- distinguish deterministic checks from model judgment

## Desired User Experience

### Workshop mode

When the user edits story text, Laires should:

- mark the affected scene or scenes as stale immediately
- show that re-analysis is pending
- auto-run incremental analysis after a short debounce or on explicit save
- refresh graph-derived views
- show a compact "change review" summary

Example:

> Re-analyzed Scene 4 after your edit. Conflict clarity improved, but Elena's objective is now less explicit. Pacing unchanged. 1 continuity warning introduced.

### Consultant mode

When the user asks whether a proposed revision helps, Laires should:

- simulate or inspect the changed scope
- compare narrative state before and after
- explain the tradeoff in story terms
- optionally add recommendations to the revision brief

### Full review

The user should still be able to explicitly request:

- `Re-scan changed scenes`
- `Review this chapter`
- `Reassess the whole story`

## Trigger Model

The loop should trigger on any user action that can invalidate narrative analysis.

### Automatic triggers

- Canvas text edits in Workshop mode
- Agent-applied edits via canvas tools
- Scene insertion, deletion, split, merge, or move
- Changes to context files that influence interpretation
- Accepting a revision generated by the agent

### Semi-automatic triggers

- Save file
- Switch away from a dirty scene
- Open a panel whose results are stale

### Manual triggers

- `Re-scan`
- `Review this change`
- `Review chapter`
- `Full story review`

## Cost Model

The default path must be incremental.

### Cheap path

- detect changed byte ranges
- map them to scene IDs
- re-run LLM analysis only for changed scenes
- recompute graph neighborhoods and deterministic evaluators locally

### Escalation path

Broaden the scope only when local signals suggest wider narrative fallout:

- scene order changed
- character introduction/removal changed downstream expectations
- objective/conflict topology changed substantially
- declared intent now diverges in multiple places
- the user explicitly asks for broader review

### Full review path

Only on explicit request or major structural edits:

- re-analyze many or all scenes
- rerun story-wide evaluators
- generate a manuscript-level before/after assessment

## Architecture Overview

```
User edit
  -> dirty/stale marking
  -> impact scope computation
  -> incremental re-analysis
  -> graph patch application
  -> local evaluators
  -> before/after diff
  -> user-facing change review
```

## Core Concepts To Add

### 1. Change scope

Represents what changed and how broad the review should be.

Suggested shape:

```rust
pub struct ChangeScope {
    pub reason: ChangeReason,
    pub changed_files: Vec<String>,
    pub changed_scene_ids: Vec<String>,
    pub neighboring_scene_ids: Vec<String>,
    pub affected_character_ids: Vec<String>,
    pub requires_storywide_eval: bool,
}
```

### 2. Story evaluation snapshot

Captures narrative metrics before and after a change.

Suggested shape:

```rust
pub struct StoryEvalSnapshot {
    pub scene_count: usize,
    pub stale_scene_count: usize,
    pub dead_scenes: Vec<String>,
    pub divergences: Vec<Divergence>,
    pub pacing_summary: PacingSummary,
    pub conflict_density: ConflictDensitySummary,
    pub arc_completeness: ArcCompletenessSummary,
}
```

### 3. Change review

User-facing summary of what improved or regressed.

Suggested shape:

```rust
pub struct ChangeReview {
    pub scope: ChangeScope,
    pub before: StoryEvalSnapshot,
    pub after: StoryEvalSnapshot,
    pub improvements: Vec<String>,
    pub regressions: Vec<String>,
    pub unresolved_risks: Vec<String>,
    pub confidence: ReviewConfidence,
}
```

## Phase Plan

### Phase 1: Staleness and trigger plumbing

Goal: make the app reliably know when analysis is stale and why.

Changes:

- introduce explicit dirty and stale review state in GUI/domain state
- on `CanvasTextChanged`, compute changed ranges and affected scenes
- record a pending `ChangeScope`
- add debounce scheduling for auto-review
- expose stale status in the UI

Implementation notes:

- start from existing `CanvasTextChanged` handling in [agent.rs](/Users/justingibbs/Projects/laires/src/gui/agent.rs#L214)
- reuse existing scene map and pending analysis concepts instead of inventing a second invalidation system
- do not trigger an LLM call on every keystroke

Milestone:

- after an edit, the app visibly marks the relevant scenes and panels as stale

### Phase 2: Incremental re-analysis engine

Goal: rerun LLM analysis only for impacted scenes.

Changes:

- add a dedicated incremental review entry point in the GUI agent loop
- build a `ChangeScope` from changed scenes
- re-run scene analysis for changed scenes only
- patch graph state for only those scenes
- preserve unchanged graph state

Implementation notes:

- refactor current `run_gui_scan` behavior into reusable full-scan vs incremental-scan paths
- keep changed-scene analysis as the primary unit of LLM work
- allow optional inclusion of immediate neighboring scenes for better narrative continuity judgments

Milestone:

- a single-scene edit causes only that scene, or a narrowly expanded scope, to be re-analyzed

### Phase 3: Deterministic evaluator pass

Goal: compute cheap post-change checks locally after graph updates.

Evaluators:

- dead scene detection
- divergence detection
- pacing summary
- conflict density
- arc completeness
- stale coverage

Changes:

- define a common evaluator interface
- compute an evaluation snapshot before applying graph updates
- compute another after updates
- store both snapshots for diffing

Milestone:

- Laires can produce a structured local before/after narrative diff without another broad LLM call

### Phase 4: Before/after change review

Goal: give the writer a clear verdict on the change.

Changes:

- introduce `ChangeReview`
- generate user-facing summaries from snapshot diffs
- classify results into improvements, regressions, and risks
- show confidence based on how much of the result is deterministic vs model-derived

UI surfaces:

- chat/tool output
- dashboard review card
- scene-level status badge
- optional "latest review" panel

Milestone:

- after an edit, the app can say what changed in narrative terms, not just that a scan ran

### Phase 5: Escalation rules for broader review

Goal: avoid full reruns for small edits while still catching structural fallout.

Escalation inputs:

- multiple scenes changed in one session
- changed objective/conflict topology
- character presence changes
- chapter-level reorder
- user asks a storywide question

Changes:

- define scope expansion heuristics
- expand from scene to chapter or story only when thresholds are crossed
- record why escalation happened

Milestone:

- broader review happens intentionally and explainably, not unpredictably

### Phase 6: UI integration

Goal: make the loop visible and controllable.

Additions:

- stale badge in sidebar scene list
- "Review pending" indicator in top/status bar
- "Re-analyze now" action
- "Last change review" card on Dashboard
- optional per-scene change summary in Canvas or Inspector

UX rules:

- auto-review should be unobtrusive
- full review should always be explicit
- the user should never wonder whether displayed analysis reflects current text

Milestone:

- the app communicates freshness and review outcomes clearly

### Phase 7: Tests and fixtures

Goal: validate the loop as product behavior, not just utility code.

Test classes:

- changed-range to scene-scope mapping
- incremental graph update correctness
- evaluator snapshot diffing
- escalation thresholds
- GUI state freshness transitions
- end-to-end story change loop on fixture manuscripts

Suggested fixtures:

- a one-scene line edit with no structural change
- a scene rewrite that changes objective clarity
- a scene insertion that affects pacing
- a character removal that creates arc incompleteness

Milestone:

- the story-change loop is regression-tested as a harness behavior

Recommended implementation order:

5. Escalation heuristics
6. Dashboard and sidebar review UI
7. End-to-end tests

## Non-Goals

These are explicitly out of scope for the first implementation:

- full autonomous manuscript rewriting
- always-on full-book reevaluation after every edit
- speculative scoring of literary quality across all dimensions
- replacing human judgment with a single numeric score

## Success Criteria

The feature is successful when:

- small edits trigger cheap, incremental re-analysis
- the app clearly marks stale vs fresh analysis
- the user can see what improved or regressed after a change
- storywide reruns happen only on explicit request or justified escalation
- Laires feels closer to a fiction harness than a passive story IDE

## Open Questions

- should auto-review run on debounce, save, or both by default
- should neighboring scenes be included by heuristic or only when explicitly requested
- how much of the change review should be deterministic vs LLM-generated prose
- should Consultant mode support hypothetical before/after review without applying edits
- should revision brief entries be generated automatically from regressions
